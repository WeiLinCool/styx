# 管理端文档中心运营化重构设计

日期：2026-06-05

## 1. 背景

当前文档中心首版已经具备数据库模型、前台阅读页、管理端文章列表、分类巡检、Markdown 导入与文章编辑能力，但管理端存在四个直接影响运营落地的问题：

- 文档列表筛选不可用，运营无法稳定定位目标文档
- 新建文档流程依赖原始字段组合，操作路径不清晰
- 分类目录页面基本只读，无法形成目录维护闭环
- 文档内容编辑直接暴露 `内容块 JSON`，不适合初级运营人员

这些问题的共同根因不是底层模型缺失，而是管理端把开发者视角的数据结构直接暴露给运营，导致结构存在、流程不存在。

## 2. 目标与非目标

### 2.1 本轮目标

- 把文档中心管理端改造成适合初级运营使用的任务型后台
- 修复文档列表的筛选链路，使关键词、状态、分类筛选真正生效
- 把分类目录从只读巡检页升级为可维护的两级目录管理页
- 把文章编辑器从 JSON 文本框升级为块列表编辑器
- 在不改变持久化真相的前提下，降低日常维护门槛

### 2.2 明确不做

- 不做无限级分类
- 不做审批流、版本历史、回滚
- 不做多人协作与锁定
- 不做拖拽排序第一版
- 不重做前台 `/docs` 阅读信息架构
- 不新增第二套内容存储模型

## 3. 问题归类

本次改造属于 `Large`：

- 涉及用户可见的管理端信息架构变化
- 涉及页面、API、feature UI、repository 的跨边界改动
- 涉及内容状态和目录维护的操作约束

## 4. 现状观察

当前代码中的关键现实：

- `/admin/docs` 与 `/admin/docs/articles` 都直接调用 `getAdminDocsModuleData()`，没有接收 URL 查询参数，也没有把筛选条件传入 repository
- `src/features/admin/admin-doc-editor.tsx` 以 `Textarea` 直接维护 `blocksJson`
- `/admin/docs/categories` 页面文案明确写明“当前版本先通过 API 建分类，页面侧提供只读巡检”
- repository 已具备 `parentId` 字段和分类/文章/块三张核心表，说明现有数据模型足以支撑两级目录与块化内容

结论：问题主要在管理端工作流与交互层，不在数据库建模层。

## 5. 设计原则

### 5.1 内容真相唯一

文档内容的持久化真相仍然是 `doc_article_blocks`。UI 可以改成块列表编辑器，但不能引入第二套富文本真相或编辑器专属存储格式。

### 5.2 运维面任务化

管理端页面按运营任务划分，而不是按底层实体裸暴露。用户应该先看到“找文档、建文档、改目录、导入文档”这些动作，而不是先面对 JSON 与只读数据卡片。

### 5.3 目录与发布 fail closed

分类缺失、内容块非法、标题或 slug 缺失时，文档不能发布。删除分类若会破坏目录或孤立文章，必须阻止。

### 5.4 控复杂度优先于炫技

第一版优先显式操作和可解释错误，不优先拖拽、复杂富文本或隐式自动化。

## 6. 外部参考与可迁移原则

### 6.1 Shopify Polaris

Reference: https://polaris-site-prod-kit.shopify.prod.shopifyapps.com/components/selection-and-input/index-filters

- Promise: 资源列表的筛选、搜索、排序应形成单一稳定工作区
- State owner: 列表状态由页面和数据查询链路共同拥有
- Invariants:
  - 筛选项必须真实接到数据源
  - 应优先暴露最高频的少量筛选维度
- Transferable principle: 后台筛选不是视觉控件问题，而是“UI 状态 -> 查询参数 -> 数据返回”的闭环
- Not directly copied because: 本仓库是 App Router + repository 查询，不使用 Polaris 组件体系

### 6.2 Notion Blocks

Reference: https://www.notion.com/help/category/write-edit-and-customize

- Promise: 非技术用户可以按块组织内容，而不需要理解底层结构
- State owner: 页面内容仍由结构化块拥有
- Invariants:
  - 内容由有序 blocks 构成
  - 每个 block 独立编辑、移动、删除
- Transferable principle: 把内容拆成小块并显式管理顺序，比直接暴露原始结构更适合低门槛运维
- Not directly copied because: 本仓库不需要自由富文本宇宙，只需要有限块类型的后台文档编辑

Industry consensus -> Transferable principle -> This repository's constraints -> Local design

- Industry consensus: 成熟后台把筛选作为真实查询闭环，把长文编辑做成块化而不是原始结构暴露
- Transferable principle: 后台操作面应按任务建模，编辑器应按块建模
- This repository's constraints: Next.js App Router、`src/server/repositories` 持有查询真相、现有 docs 表结构已落地、需要兼容旧文章块数据
- Local design: 保留现有表结构，重做管理端信息架构、筛选链路与块编辑交互

## 7. 作用域与边界

### 7.1 边界图

- Page/UI: `src/app/admin/(console)/docs/**`, `src/features/admin/**`
- API boundary: `src/app/api/admin/docs/**`
- Domain/persistence: `src/server/repositories/docs.ts`
- Database truth: `doc_categories`, `doc_articles`, `doc_article_blocks`

### 7.2 责任划分

- Route handlers: 校验输入、返回结构化错误
- Feature UI: 渲染列表、编辑器、分类管理交互，不拥有持久化真相
- Repository: 列表筛选查询、分类增删改约束、文档写入归一化
- Database: 分类层级、文章归属、块顺序的持久约束

## 8. 不变式

1. 文档内容写入时必须归一化为合法 `DocBlock[]`
2. 分类层级最多两级，二级分类不能再拥有子分类
3. 文档发布前必须满足分类、标题、slug、内容块合法性校验

## 9. 信息架构

管理端文档中心统一为四个任务入口：

- `/admin/docs`
  - 文档列表工作台
  - 负责搜索、筛选、查看状态、进入编辑页、创建新文档
- `/admin/docs/articles/new` 与 `/admin/docs/articles/[articleId]`
  - 文档创建与编辑
  - 负责文章基础信息与块内容维护
- `/admin/docs/categories`
  - 分类目录管理
  - 负责两级目录维护、排序、受众范围调整
- `/admin/docs/import`
  - Markdown 导入辅助页
  - 负责从已有 Markdown 生成草稿后跳转到编辑页

这样划分后：

- 日常运维先进入列表页
- 目录维护进入分类页
- 单篇内容维护进入编辑页
- Markdown 只做辅助输入，不再承担主要编辑职责

## 10. 分类目录设计

### 10.1 目标

把当前只读分类巡检页改成真正的两级目录维护页。

### 10.2 支持的操作

- 新建一级分类
- 在一级分类下新建二级分类
- 编辑分类：
  - `name`
  - `slug`
  - `description`
  - `audienceScope`
  - `sortOrder`
- 删除分类

### 10.3 层级规则

- 一级分类可拥有二级分类
- 二级分类不能继续创建子分类
- 系统不支持第三级

### 10.4 删除与安全约束

- 若一级分类下仍有子分类，不允许删除该一级分类
- 若分类下仍有关联文章，不允许删除该分类
- 删除失败时返回面向运营的明确提示，而不是数据库错误

### 10.5 文章归属规则

- 文档可以挂到一级或二级分类
- 若某一级分类已经拥有子分类，UI 默认提示优先把新文章挂到二级分类，避免目录混乱

## 11. 文档列表与筛选设计

### 11.1 问题定义

当前列表页虽然显示筛选与搜索控件，但筛选状态没有进入查询链路，导致“看起来能筛，实际上不筛”。

### 11.2 本轮支持的筛选维度

- 关键词
  - 匹配标题、slug、摘要、分类名
- 状态
  - `all`
  - `draft`
  - `published`
  - `archived`
- 分类
  - 以分类 ID 为筛选值

### 11.3 状态归属

- 筛选条件属于列表页 URL 查询参数
- Page 负责读取 `searchParams`
- Page 将参数传给 repository
- Repository 负责唯一业务查询解释

### 11.4 预期行为

- 刷新页面后筛选条件保持不丢失
- 复制 URL 后可复现相同结果
- 列表顶部筛选标签与结果一致
- “全部/草稿/已发布/已下线” quick filters 与分类/关键词组合时不互相覆盖

## 12. 新建文档与编辑页设计

### 12.1 基础信息

编辑页顶部保留文章基础信息：

- 所属分类
- 状态
- 标题
- slug
- 摘要
- 封面图 URL

### 12.2 新建默认行为

- 默认状态为 `draft`
- 必须先选择分类
- 默认创建至少一个基础文本块，避免空白编辑器
- slug 可由标题自动生成，也允许手动覆盖

### 12.3 保存与状态控制

- 点击“保存”只执行内容保存，不自动发布
- 已发布文章保存时仍需经过完整合法性校验
- 若保存后的内容不满足发布约束，已发布文章不得保留为不合法发布态

## 13. 块列表编辑器设计

### 13.1 总体形式

编辑器从 `内容块 JSON` 改为 `块列表 + 单块表单` 模式。

建议布局：

- 上方：文章基础信息
- 下方左侧：块列表
- 下方右侧或折叠区：当前块编辑表单

### 13.2 每个块支持的动作

- 选中
- 编辑
- 上移
- 下移
- 删除
- 在当前块后新增新块

第一版不做拖拽排序，优先显式按钮。

### 13.3 首批支持的块类型

基于当前仓库现有块模型与运营使用场景，第一版以高频块为主：

- `paragraph`
- `heading`
- `list`
- `callout`
- `image`
- `faq`
- `quote` 或当前模型中的等价说明块

原则：

- 优先覆盖大多数说明文档场景
- 不在第一版引入复杂多媒体编排
- 对暂未可视化支持的旧块，提供只读提示或保守兜底，不强行破坏旧数据

### 13.4 校验方式

每个块在前端先做基础校验，例如：

- 标题不能为空
- 段落不能为空
- 图片块必须有图片地址
- FAQ 问答项必须完整
- 列表块至少有一项

错误提示要定位到具体块，例如：

- `第 3 个内容块：FAQ 答案不能为空`
- `第 5 个内容块：图片地址缺失`

### 13.5 旧数据兼容

- 旧文章仍从 `doc_article_blocks` 读取
- 进入编辑器时映射成 UI 可编辑状态
- 保存时再映射回标准块结构
- 不做数据库迁移

## 14. Markdown 导入定位

Markdown 导入继续保留，但职责调整为辅助入口：

- 导入 Markdown
- 生成草稿文章与块结构
- 自动跳转到文章编辑页
- 由运营在块编辑器中继续修订

它不再是主编辑方式，也不再要求运营理解导入后的 JSON 结构。

## 15. 状态流与恢复行为

### 15.1 状态定义

- `draft`
- `published`
- `archived`

### 15.2 合法流转

- `draft -> published`
- `published -> archived`
- `archived -> draft`

### 15.3 发布前检查

发布必须验证：

- 分类存在
- 标题存在
- slug 存在
- 内容块数组非空
- 每个块满足 schema

任何条件不满足时：

- 拒绝发布
- 返回可操作错误消息

## 16. 可用性目标

本轮不是做一个“功能更强”的 CMS，而是做一个“初级运营不需要理解底层结构也能完成工作”的后台。

成功标准：

- 初级运营可在列表页通过搜索与筛选找到文章
- 初级运营可独立创建两级分类并理解目录关系
- 初级运营可不接触 JSON 完成常规文档维护
- Markdown 导入后的后续维护不需要开发介入

## 17. 风险与缓解

### 17.1 旧块类型与新编辑器覆盖不一致

风险：

- 已有文章可能含有新编辑器未覆盖的块类型

缓解：

- 实现前先枚举现有块类型
- 未覆盖类型以只读警示或保守回显处理
- 不在首轮强制迁移

### 17.2 分类删除破坏前台阅读路径

风险：

- 删除目录可能造成文章失联或前台路径变化

缓解：

- repository 层禁止删除仍有关联文章或子分类的目录

### 17.3 筛选只在前端做导致数据不一致

风险：

- 页面显示与真实数据查询不一致

缓解：

- 列表筛选以 repository 查询为真相
- 前端只表达当前参数，不重复定义业务语义

## 18. 验证策略

最低有效验证层如下：

- Repository 级：
  - 筛选条件组合查询
  - 分类删除约束
  - 分类创建/更新层级约束
  - 文档发布合法性检查
- Feature/UI 级：
  - 块编辑器增删改排序
  - 表单错误定位
  - 列表筛选状态与 URL 同步
- 基线：
  - `pnpm validate`
  - `pnpm build`
- 浏览器验证：
  - `/admin/docs`
  - `/admin/docs/categories`
  - `/admin/docs/articles/new`

## 19. 实施建议

建议按以下顺序实施：

1. 修复列表筛选链路
2. 完成分类目录管理页与对应 API/repository 写路径
3. 把编辑器从 JSON 改为块列表编辑器
4. 收口新建文档默认行为与导入后的跳转链路

这样可以先恢复“找得到”，再解决“能维护”，最后解决“好维护”。
