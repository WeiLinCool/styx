# 全站 UI 规范与主题治理设计

日期：2026-06-04

## 背景

当前仓库已经开始接入明暗主题系统，但整体 UI 仍处于“局部适配、规则分散”的状态：

- 全局主题真相源已建立，但大量页面仍保留硬编码浅色样式。
- 用户端与管理端存在不同程度的局部视觉写法，尚未回收到统一规范。
- 现有页面常直接使用 `bg-white`、`text-[#...]`、`border-black/...`、`border-neutral-200` 等固定颜色，导致夜间模式难以完整覆盖。
- 缺少一份对未来开发有约束力的全站 UI 规范，页面容易继续长出新的例外。

本次变更目标不是再补几个页面，而是建立一套**强约束的全站 UI 规范**，并将现有页面逐步整改到该规范下，确保以后所有页面都必须兼容 `light / dark / system` 主题切换。

## 范围

本次覆盖以下范围：

- 定义一份全站强约束 UI 规范。
- 规范主题状态、颜色 token、表面层级、边框、阴影、文本层级、状态色、表单、表格、卡片、弹层与交互状态。
- 规定允许与禁止的视觉实现方式。
- 将规范落到全局 token、共享组件和共享页面骨架。
- 分批整改现有页面，使其兼容明暗主题切换。
- 建立以后页面开发必须遵守的主题兼容约束。

明确不做：

- 不引入多品牌、多租户主题系统。
- 不在本次重构业务逻辑、鉴权、仓储或 API 边界。
- 不将本次升级扩大为全站全量视觉重设计。

## 任务分类

这是一个 Large 任务，因为它包含：

- 全站级设计规范建立。
- 共享样式、共享组件与大量页面的跨边界整改。
- 用户端与管理端两个表面的长期治理约束。

## 现状与可复用基础

### 已有基础

- 全局布局：
  - `src/app/layout.tsx`
- 全局样式与主题 token：
  - `src/app/globals.css`
- 共享 UI 组件：
  - `src/components/ui/*`
- 已有主题接线：
  - `src/components/theme/theme-provider.tsx`
  - `src/components/theme/theme-toggle.tsx`
- 用户端与管理端当前已部分接入的页面：
  - `src/features/public/home-page.tsx`
  - `src/features/public/my-assets-page.tsx`
  - `src/features/admin/admin-shell.tsx`
  - `src/features/admin/admin-header.tsx`
  - `src/features/admin/module-page.tsx`

### 当前问题

- 视觉规则主要存在于页面局部，而不是存在于系统层。
- 用户端 AI 工具页、用户中心、权益页、工作流页、聊天页等仍有大量硬编码浅色样式。
- 管理端业务页虽然共享壳层部分已接入主题，但大量 feature module 和详情/配置界面依旧依赖固定浅色。
- 缺少针对未来开发的“禁止项”与“唯一允许路径”。

## 状态所有权

| 状态 | Owner | 写入口 | 真相来源 |
| --- | --- | --- | --- |
| 当前主题模式 `light/dark/system` | 全局 ThemeProvider | 主题切换器 | `next-themes` 本地持久化 + `html` class |
| 设计 token | `src/app/globals.css` | 代码定义 | CSS 自定义属性 |
| 共享组件视觉基线 | `src/components/ui/*` | 组件实现 | 语义 token |
| 页面视觉组合 | `src/app/*` / `src/features/*` | 页面布局与组合 | 共享组件 + 规范允许的 token |
| 例外样式 | 明确批准的有限场景 | 代码定义 | 规范允许的特殊用途 |

## 不变量

1. 整个 WebUI 只能有一个全局主题真相源，用户端和管理端不得维护独立主题状态。
2. 所有页面必须兼容 `light / dark / system` 三态。
3. 页面主视觉颜色必须来自语义 token，不得直接依赖硬编码浅色/深色值。
4. 用户端与管理端允许信息密度不同，但不得演化成两套独立设计系统。
5. 共享组件的视觉规则高于页面自由发挥，页面负责组合，不负责重新发明组件视觉体系。

## 方案选择

### 方案 1：强约束规范 + token 治理 + 共享组件收口 + 分批整改

做法：

- 先编写一份强约束的全站 UI 规范。
- 将颜色与组件规则落入全局样式和共享组件。
- 再按页面批次整改现有硬编码样式。
- 后续所有页面必须以该规范为唯一允许路径。

优点：

- 规范可执行，而不是只停留在文档。
- 可以约束未来页面不再回到硬编码颜色。
- 用户端与管理端可以共享同一视觉治理模型。

缺点：

- 首轮需要处理较多现存页面。

### 方案 2：只写规范文档，页面逐步人工遵守

优点：

- 初始成本低。

缺点：

- 约束力弱。
- 旧问题会反复出现。

### 方案 3：新建第二套设计系统并重写现有页面

优点：

- 理论上最彻底。

缺点：

- 成本过高。
- 会把主题兼容问题升级成大规模重构。

### 推荐

采用方案 1。

## 参考研究

### Industry consensus

- 成熟产品会将主题、颜色、表面层级与组件规则统一沉淀到 token 和共享组件，而不是分散到页面。
- Dark Mode 不应依赖简单反色，而应使用分层表面、受控对比和统一语义色。
- 设计系统要有强约束能力，否则组件层之上会持续出现页面级例外。

参考：

- https://developer.apple.com/design/human-interface-guidelines/dark-mode
- https://developer.apple.com/design/human-interface-guidelines/ios/visual-design/dark-mode

### Transferable principle

- 主题不是页面功能，而是全站基础设施。
- 颜色不是视觉自由项，而是系统级语义资源。
- 共享组件和共享页面骨架是设计约束的主要落点。

### This repository's constraints

- 当前仓库已具备 Tailwind v4 token 映射和 `next-themes` 接线。
- 现有页面中有大量手工视觉样式和高频硬编码颜色。
- 管理端和用户端共享代码仓，但面向不同信息密度场景。

### Local design

- 建立一份强约束规范。
- 用 token、共享组件和共享壳层承载规则。
- 用分批整改替代一次性重写。

## 最终设计

### 一、主题与颜色治理

#### 主题状态

- 全站仅支持三态：
  - `light`
  - `dark`
  - `system`
- 默认值为 `system`。
- 用户显式选择可覆盖系统设置。

#### 颜色来源规则

- 页面主视觉颜色必须来源于语义 token。
- 核心 token 至少包括：
  - `background`
  - `foreground`
  - `card`
  - `popover`
  - `primary`
  - `secondary`
  - `muted`
  - `accent`
  - `destructive`
  - `border`
  - `input`
  - `ring`
  - `sidebar`
- 应补充语义状态层：
  - `success`
  - `warning`
  - `info`
  - 对应的前景与弱表面色

#### 亮色主题原则

- 亮色主背景不得为纯白大平面。
- 使用灰白基底和低对比边框降低刺眼感。
- 强调色仅用于交互焦点、主 CTA 与可点击高亮，不得泛滥。

#### 深色主题原则

- 深色主背景不得退化为整页纯黑。
- 卡片、侧栏、浮层、输入和分隔线必须保留层级。
- 文本颜色需使用柔白与次级灰白分层，而不是全部拉满对比。

### 二、表面层级规范

- 页面背景：`background`
- 一级容器：`card`
- 浮层、下拉、对话框：`popover`
- 侧栏与后台导航：`sidebar`
- 弱信息区、占位区、空状态辅助面：`secondary` 或 `muted`

约束：

- 页面不得自行定义新的“容器基底色体系”。
- 同一页面中容器层级必须与全站规则一致。

### 三、组件外观规范

#### 按钮

- 只允许使用共享按钮变体或在其基础上做受控扩展。
- 主按钮使用 `primary`。
- 次按钮使用 `outline` 或 `secondary`。
- 危险操作统一使用 `destructive` 语义。

#### 输入类控件

- 输入框、文本域、选择器、切换器、单选/复选均必须依赖共享组件基线。
- 页面内不得重新定义一套输入视觉规范。

#### 卡片与面板

- 所有信息卡片、参数面板、结果面板都必须使用统一表面层级。
- 夜间模式下必须保持边界可辨识。

#### 表格与后台模块

- 后台表格页统一使用共享容器、共享卡片、共享表格基线。
- 列表、筛选条、统计卡、状态 badge 不允许各页再自定义一套浅色样式。

#### 弹层与模态

- Dialog、Dropdown、Popover、Toast 统一跟随当前主题。
- 弹层背景与边框一律使用 `popover` / `border` 体系。

### 四、文本与状态层级

- 文本至少分为：
  - 主文本
  - 次文本
  - 弱提示文本
- 状态色必须统一映射：
  - 成功
  - 警告
  - 危险
  - 信息

约束：

- 页面不得自行挑选“看起来差不多”的颜色代替状态语义。

### 五、阴影、边框与交互状态

- 阴影必须作为层级辅助，而不是主要边界来源。
- 边框必须统一走语义 `border` 或状态边框色。
- hover / active / focus / disabled 必须在 light 与 dark 下都可辨。
- 焦点高亮一律走 `ring` 体系。

### 六、允许项与禁止项

#### 允许项

- 使用语义 token。
- 使用共享组件或共享页面壳层。
- 对图表、品牌图标、素材内容保留明确用途的特殊颜色。

#### 禁止项

- 禁止在页面主视觉中直接写：
  - `bg-white`
  - `text-black`
  - `text-[#...]`
  - `border-black/...`
  - `border-neutral-200`
  - 大面积固定浅色或固定深色背景
- 禁止为用户端和管理端创建独立主题上下文。
- 禁止通过零散 `dark:` 补丁取代语义 token 治理。
- 禁止新增页面绕开共享组件重写视觉基线。

### 七、实现落点

#### 全局层

- `src/app/globals.css`
  - 维护唯一主题 token
  - 维护表面层级、滚动条、全局底色与文本色

#### 共享组件层

- `src/components/ui/*`
  - 统一承载按钮、输入、表格、卡片、弹层、状态组件视觉规则
- `src/components/theme/*`
  - 承载主题 provider 与切换器

#### 页面骨架层

- 用户端共享壳层、管理端共享壳层、共享模块页应尽量承担页面基线。

#### 页面层

- 页面只组合规范允许的组件和 token。
- 页面不得自建颜色体系。

### 八、现有页面整改策略

整改分批执行：

1. 用户端 AI 工具页：
   - `chat`
   - `image-gen`
   - `video-gen`
   - `workflow`
2. 管理端高频业务页：
   - 后台首页
   - 用户、订单、会员、权限、内容、AI 模型、AI 任务、帮助中心等
3. 高频用户页：
   - `user-center`
   - `membership`
   - `gallery`
   - `shop`
   - 权益页等
4. 营销/内容/长尾页面

整改原则：

- 先收口共享容器和共享组件，再补页面特殊区块。
- 不接受“看起来差不多”的局部修色，必须回到 token 体系。

### 九、以后开发的强约束机制

- 新页面必须默认支持 `light / dark / system`。
- 新页面不得引入主视觉硬编码颜色。
- 共享组件优先级高于页面自由样式。
- 如需例外，必须满足：
  - 有明确业务理由
  - 不破坏主题切换
  - 不创建新的基础色体系

建议后续增加一条工程化检查：

- 用 lint 规则或静态扫描拦截高风险硬编码颜色写法。

## 风险与缓解

### 风险 1：整改范围大，容易遗漏页面

缓解：

- 按页面批次推进。
- 每批用 `rg` 搜索高风险硬编码颜色。

### 风险 2：共享组件规则和页面历史写法冲突

缓解：

- 优先修共享壳层和共享模块页。
- 再处理历史页面的局部例外。

### 风险 3：夜间模式下后台高密度页面对比不足

缓解：

- 后台优先使用卡片层级、状态 badge 和表格边框统一规范。
- 在 dark 下重点验证输入、筛选条、表格、状态块。

## 验证策略

- 文档层：
  - 规范文档无占位符、无模糊禁止项、无冲突规则
- 代码层：
  - `pnpm validate`
  - `pnpm build`
- 页面层：
  - 每批整改后验证 `light / dark / system`
  - 验证用户端 AI 工具页
  - 验证管理端主要业务页
- 治理层：
  - 用检索或规则确认新增代码未继续引入高风险硬编码颜色

## 成功标准

- 仓库存在一份强约束的全站 UI 规范。
- 主题切换成为全站基础能力，而不是局部页面特性。
- 现有页面开始系统性回收到共享 token 和共享组件规则。
- 后续页面开发必须遵守统一 UI 与主题治理路径。
