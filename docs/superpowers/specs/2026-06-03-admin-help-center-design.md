# 管理端帮助中心设计

## 背景

当前管理端已经覆盖用户、会员、权益、订单、AI 任务、AI 模型、Agent 能力、合作、内容、权限、设置等模块，但这些页面主要承担操作入口职责，缺少一个统一的帮助页来解释：

- 各模块分别负责什么。
- 模块之间如何形成上下游关系。
- 后台配置如何影响前台用户侧功能。
- Agent 能力层和数据持久化层在整体链路中的位置。

本次新增一个管理端一级页签 `帮助中心`，作为后台运营知识入口和模块地图，帮助新成员和日常运营快速建立全局理解，并能从说明直接跳转到对应模块页面。

## 目标

- 在管理端新增一级导航 `帮助中心`。
- 提供一个可阅读、可跳转的模块关系说明页。
- 同时覆盖后台模块、前台用户侧、Agent 能力层、数据与规则层之间的关系。
- 首版以静态内容为主，但复用已有管理端导航路径，避免说明页和真实入口漂移。

## 非目标

- 不建设 CMS 或动态知识库系统。
- 不从路由自动生成整页帮助内容。
- 不在首版引入复杂流程图编辑器、可拖拽关系图或搜索系统。
- 不改变现有业务模块的权限、状态流转或数据结构。

## 参考原则

行业共识：

- 成熟后台文档入口通常采用“中心化帮助页 + 按职责分组 + 每块同时提供说明与操作入口”的结构。
- 关系说明应先给全局视角，再给模块级操作上下文，避免只有图没有行动入口，或只有卡片没有整体认知。

可迁移原则：

- 帮助中心应先回答“这个模块是做什么的、影响什么、去哪里操作”，再补充细节。
- 真实跳转路径应尽量复用现有导航定义，降低维护成本。

本仓库约束下的落地：

- 页面保持 WebUI-first 的管理台风格，采用现有 admin shell 和 UI 基元。
- 内容以静态配置渲染，跳转目标复用现有管理端路由。

## 用户与使用场景

主要用户：

- 新加入的运营或客服成员。
- 需要跨模块排查问题的后台管理员。
- 需要理解前台功能为何呈现为当前状态的产品或技术同学。

典型场景：

- 想知道某个前台功能是由哪些后台模块共同决定的。
- 想知道某个后台配置改动会影响哪些前台页面或业务结果。
- 知道要处理某类问题，但不确定该进入哪个后台页面。

## 信息架构

新增一级页签：

- `帮助中心`

建议路由：

- `/admin/help-center`

页面采用三段结构：

1. 顶部总览
2. 模块分组说明
3. 关键链路说明

### 1. 顶部总览

顶部展示帮助中心标题、说明文案，以及一张轻量系统关系总览图。

总览图使用四层结构：

- 前台用户侧
- 管理端运营侧
- Agent / 能力编排侧
- 数据与规则侧

图的目标不是表达所有细节，而是明确：

- 前台体验由后台配置和规则共同驱动。
- 后台运营通过多个模块管理能力供给、内容发布、订单和用户状态。
- Agent 能力与 AI 模型配置共同决定 AI 类功能可用性。
- 数据库、权限绑定、发布态和状态机是最终来源。

### 2. 模块分组说明

模块说明按四组组织。

#### A. 运营与账户

- 仪表盘
- 用户
- 会员
- 权限
- 订单

该组主要解释账号生命周期、会员方案、权限绑定、订单与工单处理的关系。

#### B. 能力与供给

- 权益
- AI 任务
- AI 模型
- Agent 能力

该组主要解释用户可见能力、可用门槛、执行供给和计费映射之间的关系。

#### C. 内容与合作

- 内容
- 合作

该组主要解释前台展示内容、合作信息和相关业务触点如何由后台配置。

#### D. 基础设施与持久化

- 设置
- 数据与规则层说明

该组用于解释系统支撑层，不追求把每个底层实现展开，而是明确哪些后台动作是在改配置、哪些是在改业务状态、哪些依赖持久化与审计。

### 3. 关键链路说明

页面底部固定展示少量高价值链路，首版采用 3 条：

- 会员 / 权限 / 权益 -> 决定用户能看到和能使用什么。
- AI 模型 / Agent 能力 -> 决定前台 AI 功能的实际供给和运行方式。
- 内容 / 合作 / 订单 / 用户 -> 形成运营处理与用户触点的闭环。

## 模块卡片规范

每个模块卡片统一包含以下字段：

- 模块名称
- 模块职责
- 关联前台
- 依赖上游
- 影响下游
- 常见操作
- 快捷入口

说明：

- `模块职责` 解释该后台页面负责的核心业务。
- `关联前台` 说明它直接影响哪些用户侧页面、能力或结果。
- `依赖上游` 说明本模块的前提来源，例如方案、权限、模型或用户状态。
- `影响下游` 说明本模块变更后会波及哪些页面、状态或能力。
- `常见操作` 用短语列出运营最常做的动作。
- `快捷入口` 使用按钮或链接跳转到真实管理页。

## 内容来源与维护策略

首版采用“静态说明内容 + 复用真实入口路径”的半静态方案。

建议抽出一份帮助中心元数据配置，作为页面渲染来源，内容包括：

- 分组
- 模块名称
- 模块说明
- 上下游关系
- 入口路径

为避免说明页与导航漂移，导航路径应尽量复用现有 `adminNavItems` 中的 `href` 与 `label`，而不是在帮助中心里重复手写另一套入口常量。

如果现有导航常量未导出，则应轻量抽取共享定义供导航与帮助中心共同使用，但不扩大到自动生成整页文案。

## 视觉与交互要求

- 保持现有管理端的密集、清晰、可扫描风格。
- 页面顶部总览图保持轻量，不做复杂交互。
- 分组与模块卡片需支持桌面端快速浏览，也要兼顾移动端纵向阅读。
- 每个模块卡片必须有明确的跳转入口。
- 页面文案应直接、运营导向，避免架构术语堆叠。

## 状态与边界

可变状态：

- 帮助中心展示内容。

状态 owner：

- 管理端帮助中心页面及其对应的静态元数据配置。

写入入口：

- 代码内的帮助中心配置与页面实现。

事实来源：

- 模块关系说明以当前已存在的管理端路由、前台功能和服务边界为准。

不变量：

- 每个帮助中心模块都必须能对应到一个真实的后台模块或系统层说明。
- 每个可操作模块都必须提供可访问的后台跳转入口。
- 说明内容不能制造与现有路由、模块职责冲突的业务定义。

## 实现建议

推荐实现方式：

- 在管理端导航中新增 `帮助中心` 一级入口。
- 在 `src/app/admin/(console)/help-center/page.tsx` 新增页面。
- 在 `src/features/admin` 下新增帮助中心页面组件和配置文件。
- 复用现有管理端页面容器、卡片、按钮和排版基元。

建议的文件形态：

- `admin-help-center-config.ts`
- `admin-help-center-page.tsx`

如果需要共享导航定义，可将 `admin-nav.tsx` 中的导航项抽出为可复用常量，再由导航组件和帮助中心共用。

## 验证策略

最低验证层：

- `pnpm validate`：确认类型与 lint 安全。
- 针对导航激活与帮助中心配置可做小范围测试。
- 浏览器验证：检查新页签可见、跳转正确、页面布局与卡片分组可读。

重点风险：

- 帮助中心入口与现有导航定义不一致。
- 模块说明内容与实际后台页面职责不一致。
- 页面内容过长导致扫描效率差。
- 小屏下总览图和卡片布局可读性下降。

## 分阶段交付建议

首版只交付：

- 一级导航入口
- 总览图
- 四组模块卡片
- 三条关键链路
- 每个模块的快捷入口

后续可选增强：

- 页面内锚点导航
- 关键词搜索
- 模块负责人或最近更新时间
- 与具体后台页面的上下文互链
