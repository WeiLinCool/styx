# 统一文档中心与多模态操作说明模块设计

日期：2026-06-04

## 1. 背景与目标

当前项目已有面向管理端的静态帮助中心页面，但缺少可运营、可发布、可按角色隔离的统一文档中心能力。产品希望新增一个 doc 功能模块，用于承载系统操作说明，并同时覆盖用户端与管理端。

本次首版目标：

- 提供统一前台文档中心入口，而不是拆成两套文档站点。
- 支持按角色切换或过滤文档内容，覆盖用户端与管理端受众。
- 在管理端新增独立菜单模块，用于文档内容运维。
- 支持多模态内容展示，首版覆盖：
  - 富文本
  - 分步骤图文
  - 视频
  - 音频
  - FAQ 折叠
  - 流程图
  - 截图轮播
- 支持文档生命周期：`draft -> published -> archived`
- 支持 Markdown 单文件一次性导入，导入后可继续在后台可视化编辑。

## 2. 范围定义

### 2.1 本次实现范围

- 新增统一文档中心前台入口 `/docs`
- 新增管理端文档运维模块 `/admin/docs`
- 支持分类管理、文章管理、块内容编辑、状态流转
- 支持 7 类内容块的前台渲染与后台编辑
- 支持基于数据库的内容持久化
- 支持 Markdown 单文件导入并转成内部块模型
- 支持按受众过滤目录、文章与搜索结果
- 支持基础搜索

### 2.2 明确不进首版

- 批量 Markdown 导入
- Markdown 持续同步
- MDX 自定义组件导入
- 协同编辑
- 审批流
- 文档版本历史与回滚
- 多语言文档
- 可视化流程图拖拽编辑器
- 高级外部搜索引擎
- 公开分享链接

## 3. 设计原则

### 3.1 内容统一落为内部块模型

所有文档内容最终都必须转成平台内部块模型进行持久化和渲染。Markdown 只作为一次性导入入口，导入完成后不再作为内容源头。

### 3.2 权限与可见性在服务层收口

前台导航隐藏不等于权限控制。文档可见性必须由服务层统一判定，前端只消费服务层返回结果。

### 3.3 发布状态决定外部可见性

只有 `published` 状态的内容可进入前台目录、文章详情和搜索结果。`draft` 与 `archived` 永不对前台暴露。

### 3.4 保守解析优于错误结构化

Markdown 导入时，无法稳定识别的结构统一降级为富文本块，不为了“结构化率”牺牲内容正确性。

## 4. 信息架构

### 4.1 前台文档中心

前台采用单一入口，按用户角色过滤目录和文档内容：

- `/docs`
  - 文档首页，展示搜索框、常用入口、按角色过滤后的一级分类、最近更新
- `/docs/[categorySlug]`
  - 分类页，展示文章列表和子分类
- `/docs/[categorySlug]/[articleSlug]`
  - 文章详情页，展示目录树、文章内容、本页锚点导航

首版不拆成“用户端帮助中心”和“管理端帮助中心”两套站点，而是在同一套文档中心中根据角色呈现不同内容。

### 4.2 管理端文档运维模块

管理端新增独立菜单入口 `/admin/docs`，不继续扩展现有静态帮助中心配置。

建议首版子页面：

- `/admin/docs`
  - 总览页，显示分类数、文章数、草稿数、已发布数、导入记录摘要
- `/admin/docs/categories`
  - 分类管理页，支持层级、排序、受众范围维护
- `/admin/docs/articles`
  - 文章列表页，支持按状态、分类、受众筛选
- `/admin/docs/articles/[id]`
  - 文章编辑页，管理元信息、块内容、预览、发布动作
- `/admin/docs/import`
  - Markdown 导入页，上传文件、查看解析预览、确认导入

## 5. 领域模型

### 5.1 分类模型

`doc_categories`

字段建议：

- `id`
- `parent_id`
- `name`
- `slug`
- `description`
- `sort_order`
- `audience_scope`
- `created_at`
- `updated_at`

其中 `audience_scope` 首版建议枚举为：

- `user`
- `admin`
- `shared`

分类是文档目录的基础单位。若文章未单独声明更细粒度受众，默认继承分类可见性。

### 5.2 文章模型

`doc_articles`

字段建议：

- `id`
- `category_id`
- `title`
- `slug`
- `summary`
- `cover_image`
- `status`
- `search_text`
- `published_at`
- `archived_at`
- `created_by`
- `updated_by`
- `created_at`
- `updated_at`

文章是前台展示与后台发布的核心单位。`search_text` 由标题、摘要及块内容派生，作为首版基础搜索字段。

### 5.3 块模型

`doc_article_blocks`

字段建议：

- `id`
- `article_id`
- `block_type`
- `sort_order`
- `payload_json`
- `created_at`
- `updated_at`

首版支持的 `block_type`：

- `rich_text`
- `step_media`
- `video`
- `audio`
- `faq`
- `flowchart`
- `gallery`

`payload_json` 是不同块的结构化内容承载字段，但必须受平台内部 schema 约束，不直接等同于任意编辑器原生格式。

### 5.4 导入记录模型

`doc_import_jobs`

字段建议：

- `id`
- `source_filename`
- `source_checksum`
- `import_status`
- `error_summary`
- `preview_snapshot`
- `created_article_id`
- `created_by`
- `created_at`

该表用于记录 Markdown 导入的过程与结果。虽然首版不支持持续同步，但保留导入记录有助于审计、问题排查与运营追溯。

### 5.5 受众扩展模型

若后续需要文章级精细受众控制，可引入 `doc_article_audiences`。首版可先只做分类级受众控制，文章默认继承分类配置，减少模型复杂度。

## 6. 状态流设计

### 6.1 状态定义

文章状态仅保留三种：

- `draft`
- `published`
- `archived`

### 6.2 合法流转

- `draft -> published`
- `published -> archived`

`archived` 首版不直接恢复为 `published`。若需重新启用，应通过“复制为新草稿”的方式重新进入发布流程，以避免历史内容被静默复活。

### 6.3 外部可见性规则

- `draft`：仅后台可见，可编辑，不进入前台搜索
- `published`：前台对符合受众条件的用户可见
- `archived`：仅后台保留，不进入前台搜索

## 7. 多模态块设计

### 7.1 富文本块

用于承载常规标题、段落、列表、引用、代码块等内容，是 Markdown 导入的主要兜底块类型。

### 7.2 分步骤图文块

用于表达操作步骤。每一步建议包含：

- 步骤标题
- 步骤说明
- 配图

### 7.3 视频块

建议包含：

- 视频地址
- 封面
- 标题
- 说明

### 7.4 音频块

建议包含：

- 音频地址
- 标题
- 说明

### 7.5 FAQ 块

建议包含问答数组，每组包含：

- `question`
- `answer`

前台以可折叠方式展示。

### 7.6 流程图块

首版以结构化 JSON 或原始流程描述文本承载，前台统一渲染。首版不提供可视化拖拽编辑。

### 7.7 截图轮播块

建议包含图片数组，每张图片可附带：

- 标题
- 描述
- 排序

## 8. Markdown 导入设计

### 8.1 导入目标

首版支持上传单个 `.md` 文件，将其解析为平台内部块模型，并在确认后创建草稿文章。

该能力是“一次性导入工具”，不是持续同步源文件的内容管道。

### 8.2 导入流程

建议采用四步链路：

1. 上传 Markdown 文件
2. 服务端解析 Markdown AST
3. 将 AST 映射为内部块模型并生成预览
4. 管理员确认后写入草稿文章与块数据

### 8.3 解析映射策略

建议映射原则：

- 普通段落、标题、列表、引用、代码块
  - 归入 `rich_text`
- 可稳定识别的问答结构
  - 转为 `faq`
- 可识别的视频或音频链接
  - 转为 `video` 或 `audio`
- 图片序列
  - 转为 `gallery`
- 连续的步骤化图文结构
  - 在识别充分时转为 `step_media`
- 流程描述或流程图代码块
  - 转为 `flowchart`
- 无法稳定识别的复杂结构
  - 降级为 `rich_text`

首版不追求对所有 Markdown 语法进行完美结构化还原，保证正确导入优先于复杂结构识别。

### 8.4 导入页交互

`/admin/docs/import` 建议包含：

- 文件上传区域
- 解析结果摘要
- 内容预览区域
- 导入设置区域
  - 目标分类
  - 受众范围
  - 初始状态，默认 `draft`
  - `slug` 预填或手动调整
- 确认导入按钮

### 8.5 首版限制

- 只支持单文件 `.md`
- 不支持目录级批量导入
- 不支持持续同步
- 不支持 MDX 自定义 React 组件导入
- 不保证复杂表格与复杂嵌套结构完整结构化

## 9. 技术选型建议

### 9.1 编辑器

首版建议采用块编辑思路的现成开源方案，以降低富文本与块编辑复杂度。推荐优先考察 BlockNote，并将其作为后台编辑体验层。

但数据库中的长期真相仍然应是平台自定义 `DocBlock` schema，而不是直接将编辑器内部格式作为系统唯一内容模型。编辑器仅作为输入与编辑手段。

### 9.2 Markdown 解析

建议采用成熟的 Markdown AST 工具链，例如 `remark` / `unified` 生态，以便服务端实现稳定的一次性解析与自定义映射规则。

### 9.3 展示组件

- FAQ 使用现有折叠组件模式
- 截图轮播使用成熟轻量 Carousel 方案
- 流程图采用统一渲染器，后台首版不做拖拽编辑

## 10. 不变式

首版至少保证以下不变式：

1. 前台目录、文章详情、搜索结果只读取 `published` 内容。
2. 文档受众过滤在服务层统一计算，前端展示层不是权限边界。
3. Markdown 导入后必须落成内部块模型，后续编辑不再依赖源文件。

## 11. 风险与应对

### 11.1 Markdown 误判

风险：导入器错误识别复杂内容结构，导致展示不正确。

应对：采用保守映射策略，无法稳定识别时统一降级为 `rich_text`。

### 11.2 角色可见性泄漏

风险：前端只隐藏菜单但后端查询未过滤，导致越权查看文档。

应对：服务层统一做受众过滤，前台所有查询只接收过滤后的结果。

### 11.3 内容模型被编辑器绑死

风险：直接存储第三方编辑器内部结构，导致后续迁移和渲染受限。

应对：平台内部定义稳定的块 schema，编辑器只作为输入层。

### 11.4 发布状态被绕过

风险：草稿或归档内容出现在前台目录、详情或搜索中。

应对：所有前台查询统一限制为 `published`。

## 12. 验证策略

按最低有效层级验证：

- 纯逻辑与状态流
  - 针对状态流转、受众过滤、导入映射编写 targeted tests
- 类型与基础安全
  - 运行 `pnpm validate`
- 路由与构建连通性
  - 运行 `pnpm build`
- 数据库变更
  - 运行 `pnpm db:generate`
  - 按需运行 `pnpm db:migrate`
- 用户可见 UI
  - 浏览器验证 `/docs` 与 `/admin/docs`
  - 重点检查目录树、块渲染、导入预览、状态切换

## 13. 分阶段落地建议

### 13.1 本次交付

- 统一文档中心路由
- 后台文档运维模块
- 分类、文章、块、状态流
- 7 类块渲染
- Markdown 单文件导入
- 基础搜索

### 13.2 后续扩展

- 批量导入
- 版本历史
- 可视化流程图编辑
- 协同编辑
- 多语言内容
- 审批流

## 14. 结论

本次功能应作为独立的 docs domain 建设，而不是继续扩展现有静态帮助中心。前台采用统一文档中心，后台采用独立运维模块，内容统一持久化到数据库并以内部块模型渲染，Markdown 只作为一次性导入入口。

该方案能在控制首版复杂度的同时，覆盖用户端与管理端的操作说明场景，并为后续内容治理能力保留扩展边界。
