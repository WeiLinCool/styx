## Context

用户端之前存在一个严重问题：只按手机号建立或恢复会话，没有严格校验密码，导致任意密码都可能登录。修复这一点后，旧账号又面临一个现实问题：历史数据里并不一定已经设置过密码，因此需要拆分出“首次设置密码”流程。

对于忘记密码场景，业务要求不是短信验证，而是通过客服工单审核后发放一个临时密码，再要求用户下次登录时强制修改为正式密码。这个流程已经在页面和 API 上落地，但最早的工单实现使用 `globalThis` 内存数组存储，无法满足重启后保留记录的要求。

管理端用户页已经具备激活工单队列能力，因此密码重置工单应复用这套展示和状态流转模型，而不是另起一套孤立 UI。

## Goals / Non-Goals

**Goals:**

- 修复用户登录必须校验密码的问题。
- 为未设置密码用户提供独立的首次设置密码页面和接口。
- 为忘记密码用户提供客服工单申请入口。
- 让客服在管理端处理密码重置工单时生成临时密码，并要求用户下次登录后立即改密。
- 将密码重置工单持久化到数据库。

**Non-Goals:**

- 不接入短信验证码或外部短信网关。
- 不在这次变更中实现更复杂的 RBAC 或多因素认证。
- 不实现客户服务台之外的自助找回密码机制。

## Decisions

1. **将首次设置密码与重置密码拆成两个独立页面与接口模式。**
   - `initial` 模式仅面向从未设置过密码的历史账号。
   - `reset` 模式仅面向持有临时密码且被标记为必须改密的用户。

2. **密码重置采用工单审批，而不是短信验证码。**
   - 用户明确拒绝短信成本，因此使用客服审核工单 + 临时密码交付。

3. **密码重置工单复用管理端现有工单队列形态。**
   - 状态统一为 `pending -> processing -> closed -> archived`。
   - 管理端在用户页中与激活工单并列展示。

4. **密码重置工单必须持久化到数据库。**
   - 内存实现只适合作为过渡方案，不满足运行稳定性和审核追溯需要。

5. **临时密码登录后立即强制改密。**
   - 登录响应和 `/api/auth/me` 都返回 `mustResetPassword`，前端拿到后立即跳转到重置正式密码页面。

## Risks / Trade-offs

- **临时密码明文展示风险**：为了让客服传达给用户，办结后的工单队列会显示临时密码。这是运营需求，但需要控制后台访问权限。
- **元数据存储密码 hash 的过渡性设计**：当前密码 hash 暂存在 `users.metadata.passwordHash`，后续如果账号体系继续演进，建议迁移到更明确的专用字段或凭据表。
- **流程依赖人工客服**：用户无法自助完成忘记密码恢复，处理时效依赖客服审核效率。
