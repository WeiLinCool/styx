## Context

The repository is a root-level Next.js App Router application with user auth under `src/server/auth`, repositories under `src/server/repositories`, and AI model/provider behavior under `src/server/ai` and `src/server/repositories/ai-models`. OpenPawz enterprise desktop builds need server-side OAuth2/OIDC-like endpoints and an OpenAI-compatible model gateway. The desktop app is a public client, so it cannot safely hold a client secret and must use Authorization Code with PKCE.

The enterprise desktop user is the same durable user already managed by this application. Login SHALL reuse the existing account/password system and active-account rules. Entitlements SHALL reuse existing user entitlement configuration; this change does not add a second enterprise-only account or license table.

Industry consensus -> OAuth native app guidance favors external-browser authorization, loopback redirect URIs, and PKCE for public clients.
Transferable principle -> The server owns authorization code state, token state, expiry, and entitlement decisions.
Repository constraints -> API routes validate transport input, auth policy belongs under server auth/domain modules, repositories own durable query details, and model execution already has an OpenAI-compatible provider adapter.
Local design -> Add an enterprise server domain with thin route handlers, durable OAuth code/token records, entitlement mapping from existing user grants, and gateway routes that re-check bearer token plus `models:proxy`.

## Goals / Non-Goals

**Goals:**
- Support OpenPawz desktop OAuth2 Authorization Code with PKCE for public client `openpawz-desktop`.
- Authenticate the browser authorization flow with this application's existing user account/password login.
- Bind authorization codes and access tokens to active local users.
- Keep enterprise bearer tokens separate from WebUI cookie sessions.
- Return userinfo using existing user identity fields.
- Resolve enterprise entitlements from existing user memberships, benefits, manual grants, or equivalent active entitlement configuration.
- Expose OpenAI-compatible model listing and chat completions under `/api/llm/v1`.
- Enforce `models:proxy` or `all` on the server before model gateway access.

**Non-Goals:**
- A full external IdP federation implementation for Google, Okta, Azure AD, or SAML.
- A separate enterprise tenant, license, or entitlement administration model.
- Refresh-token rotation unless it is needed for the first desktop integration pass.
- Replacing existing WebUI login/session behavior.
- Adding new admin UI in this change.

## Decisions

### OAuth State Is Server-Owned And Durable

Authorization codes SHALL be generated by the server after successful account/password authentication, stored with a hash, and bound to `client_id`, `redirect_uri`, `code_challenge`, user ID, expiry, and consumed state. Token exchange SHALL reject expired, unknown, already-used, redirect-mismatched, client-mismatched, or PKCE-mismatched codes.

Alternative considered: stateless signed authorization codes. Rejected for the first release because one-time-use enforcement and replay investigation are clearer with repository-owned state.

### Enterprise Tokens Are Not WebUI Sessions

Enterprise access tokens SHALL be bearer tokens accepted only by enterprise APIs. They SHALL be stored hashed, expire, and resolve back to the existing user. WebUI cookie session helpers remain unchanged.

Alternative considered: returning the existing WebUI session cookie/token to the desktop. Rejected because the desktop API contract expects bearer authorization and because cookie session semantics are browser-specific.

### Authorize Login Reuses Existing Account Credentials

The `/oauth/authorize` flow SHALL validate OAuth query parameters, then authenticate the user through this application's existing user account/password logic. Only active accounts can receive an authorization code. If login fails or the user cancels, the endpoint redirects to the loopback callback with a standard OAuth error and the original `state`.

Alternative considered: requiring the user to be pre-authenticated in the WebUI before authorization. Rejected because the desktop flow should work from a fresh system browser session using the user's account credentials.

### Entitlements Are Mapped From Existing User Configuration

The enterprise entitlement API SHALL not introduce a separate source of truth. It SHALL map current user entitlement state into OpenPawz names. `models:proxy` SHALL be returned only when existing configuration grants cloud model access; `all` SHALL grant every enterprise feature.

Implementation can map from active model entitlements, membership/benefit codes, or manual grants, but the mapping must be server-side and testable. The desktop client's entitlement claims are never trusted.

### Gateway Routes Reuse Existing Model And Provider Owners

`GET /api/llm/v1/models` SHALL list enabled chat-capable models available to the bearer-token user. `POST /api/llm/v1/chat/completions` SHALL validate bearer token, entitlement, payload, and model access, then route through existing model resolution and provider adapter logic. Streaming responses SHALL use OpenAI-compatible Server-Sent Events with `data: ...` chunks and `data: [DONE]`.

Alternative considered: a mock-only gateway. Rejected for the primary implementation because the user's goal is for this project to act as the backend; tests may still include a deterministic development adapter.

## Risks / Trade-offs

- Authorization pages in App Router can blur UI and API boundaries -> keep route handlers thin and put OAuth policy in `src/server/enterprise`.
- Account/password login may currently be tied to browser cookie behavior -> isolate credential verification from cookie setting or add a domain helper that can authenticate without creating a WebUI session.
- Entitlement names may not exactly match existing benefit codes -> define a small mapping layer and tests rather than hardcoding route-level guesses.
- Bearer tokens can become long-lived credentials -> store only token hashes, enforce expiry, and keep default lifetime short.
- Gateway streaming can leak upstream errors or malformed SSE -> normalize provider errors and test `[DONE]` behavior.

## Migration Plan

1. Add durable OAuth code/token schema and generated migration.
2. Add enterprise OAuth repository and domain services for authorize, token exchange, bearer validation, userinfo, and entitlement mapping.
3. Add route handlers for OAuth, userinfo, entitlements, and model gateway endpoints.
4. Reuse existing model repository/provider adapter for available model listing and chat completions.
5. Add focused tests for OAuth validation, bearer-token authorization, entitlement mapping, and gateway responses.
6. Run database generation/migration commands, `pnpm validate`, and `pnpm build`.

## Open Questions

- Whether the first implementation should issue refresh tokens or keep only short-lived access tokens for the initial OpenPawz integration.
- Which existing entitlement code or membership/benefit rule should be treated as the canonical grant for `models:proxy` if multiple current configurations can imply model access.
